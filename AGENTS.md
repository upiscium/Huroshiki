# Repository Notes

## Environment and Checks

- Enter the pinned toolchain with `direnv allow` or `nix develop`; the shell adds Just and actionlint for development. The packaged runtime supplies Python with Textual/PyYAML/tomlkit, Packwiz, Java 21, rsync, and SSH, but deliberately excludes Just.
- Run the CI-equivalent checks locally with `nix flake check`, `nix develop --command just test-huroshiki`, `nix develop --command bash -n shared/scripts/huroshiki-launcher.sh`, `nix build .`, and `nix build .#huroshiki`. There is no configured lint, formatter, or typecheck command.
- Run one test with `PYTHONPATH=shared/scripts python -m unittest tests.test_templates.TemplateManifestTest.test_candidate_matching_ignores_loader_version -v`. Bare imports such as `import packctl` require that `PYTHONPATH` outside the Nix-provided `huroshiki` launcher.
- PTY tests are POSIX-only. The suite otherwise uses temporary repositories and mocks Packwiz where needed; it does not require a checked-in pack.

## Code Boundaries

- `shared/scripts/packctl.py` is the CLI and source of truth for project validation, YAML/TOML handling, Packwiz mutations, builds, and deployment.
- `shared/scripts/huroshiki_paths.py` resolves the managed repository as `--root`, then `HUROSHIKI_ROOT`, then the current working directory. Keep this data root separate from the installed Python/CSS source location, and do not change cwd to communicate root state.
- `shared/scripts/huroshiki.py` is only the Textual UI; keep filesystem/process behavior in `huroshiki_core.py`. Interactive Packwiz transport and output interpretation belong in `packwiz_pty.py` and `packwiz_parser.py` respectively.
- `project_locks.py` implements advisory-lock files and owner metadata; `packctl.py` validates project keys, chooses lock paths, and reexports the public lock API.
- `url_artifacts.py` owns self-hosted URL validation, DNS-pinned public-network transport, interruptible bounded downloads, JAR identity parsing, URL logs, and collision-safe Packwiz metadata writes; `portable_paths.py` owns generated metadata path/filename portability; `huroshiki_core.py` reexports the URL API and coordinates it with transactions and project configuration.
- Profile configuration loading remains in `packctl.py`; `huroshiki_core.apply_profiles` owns transactional profile execution so CLI and future TUI callers share one lock, baseline, refresh, and atomic apply.
- Packwiz additions from CLI, TUI, profiles, and templates resolve each requested root in an isolated project and merge the complete metadata closure through `resolve_mod_closure` and `merge_metadata_closure`. Side propagation is identity-based across every closure member, including unchanged installed dependencies; never reduce it to changed paths.
- One-shot template import sessions create the Pack transaction before planning and derive installed candidates only from its fixed source. Plans retain every merged Template selector and candidate-local URL verification result, preserve Template selection order, full URL selectors, effective URL policy, closure fingerprints, and verified URL JAR identities in their digest, and require resolution v3 with origin-qualified selection keys for name, URL-selector, logical-replacement, and actual-identity conflicts. Human-readable candidate keys are never resolution identities. Failed URL replacements still create logical keep-or-replace conflicts, so the installed origin can be selected without selecting the failed Template origin. Conflict choices are one global constraint set; contradictions, selected verification failures, and Pack removal without a selected replacement fail closed. Execution derives roots from selected actual identities, reuses verified URL closures, preflights every closure plus refresh before merging, and never copies Template content overlays or creates a persistent Template association.
- Closure roots are selected only by canonical provider/project ID. Resolve Modrinth IDs, slugs, and URLs through `resolve_project_selector`; CurseForge noninteractive operations require a numeric ID. Interactive labels without an explicit/resolvable ID fail closed and must never fall back to metadata names or closure ordering.
- `provider_lookup.py` is the only provider API transport. Core identity/search APIs must launch it through `run_resolver_process`, strictly validate its JSON protocol, and propagate cancellation plus absolute deadlines. CurseForge search remains unsupported; require its numeric project ID before launching Packwiz.
- TUI Install search uses `search_provider_projects` and carries canonical IDs into `ResolvedAddOperation`; do not use Packwiz menu labels to infer root identity. Search and closure resolution run off the Textual event loop and retain operation checkpoints on cancellation or failure.
- Update preparation accepts one cancellation event, an operation-wide absolute deadline, and progress callbacks. Each resolver deadline is the minimum of the operation deadline and its local cap. TUI preparation must remain off the Textual event loop and must finish resolver cleanup plus transaction discard before navigation.
- The pinned Packwiz package is `0-unstable-2026-02-18` (`packwiz --version` is unsupported). Loader-only migration uses `packwiz --yes migrate loader <version|latest|recommended>` and changes `pack.toml`; Huroshiki runs migration and refresh through `run_resolver_process`, then verifies Minecraft and loader identity before previewing the transaction.
- Noninteractive Packwiz closure resolution must use `run_resolver_process`, including process-group cancellation and a monotonic deadline. Interactive PTY cancellation remains owned by `PackwizPtySession`; URL roots retain their interruptible download cancellation and bounded network timeout.
- A resolver parent exiting does not imply its process group is finished. `run_resolver_process` inspects `/proc` for non-zombie group members, terminates post-exit descendants, and reports the run as an integrity failure; every caller must reject `orphaned_descendants`.
- `deploy_support.py` contains the pure rsync target split/join helpers, change parser/command builder, and distribution digest model; deployment configuration, preview execution, confirmation guards, and CLI behavior remain in `packctl.py`.
- Settings mutations in `packctl.py` pin and revalidate the managed collection/project directories, parse committed and local YAML from descriptor snapshots, validate the prospective merged configuration, and publish with Linux `renameat2` CAS. Post-exchange rollback must never move an external canonical replacement away; keep original and staged recovery artifacts instead. Do not replace this with path-based reopen/check/replace logic or an implicit non-atomic fallback.
- A pack lives at `packs/<id>/`: `pack.yaml` is committed configuration, `source/` is the canonical Packwiz project, and `content/common|client|server` overlays distribution content. Ignored `pack.local.yaml` may recursively override only `distribution.rsync_target`, `distribution.public_pack_url`, `minecraft_server.ssh_host`, `minecraft_server.stack_dir`, `minecraft_server.service`, `url_max_jar_size_bytes`, and `url_allow_private_networks`; all identity, Packwiz semantic, and unknown keys are invalid. The private-network opt-in is machine-local only and defaults false.
- Pack `source/` trees may contain only ordinary files and directories. Repository validation and runtime transactions use the same non-following policy and reject all symlinks and special filesystem entries before copying or Packwiz execution.
- Content overlays must not contain symlinks or Packwiz-owned names (`pack.toml`, `index.toml`, or `*.pw.toml`). Keep overlay inspection and descriptor-relative editing/copying centralized in `overlay_policy.py`; never reopen a validated overlay path by name or follow links.
- A template lives at `templates/<id>/template.yaml` and stores committed identity, Minecraft/loader settings, provider IDs, sides, and a reference loader version. Ignored `template.local.yaml` permits only `url_max_jar_size_bytes` and `url_allow_private_networks`; all other keys are invalid, and the network opt-in is prohibited in committed configuration. A template is a creation recipe, not a persistent Packwiz project; resolver projects are temporary. Any `templates/<id>/source` entry, including a symlink, is invalid.

## Generated and Operational State

- Do not edit `packs/*/dist/`; `packctl build <pack>` recreates `dist/client` and `dist/server`, filters `*.pw.toml` by `side`, overlays `common` plus the target side, then runs `packwiz refresh`.
- Every pack metadata file must have `side = "client"`, `"server"`, or `"both"`; builds stop rather than guess when classification is invalid.
- `.huroshiki/` contains ignored transaction copies and PTY logs. TUI additions are staged there and atomically applied only if the real source/template has not changed.
- Use `huroshiki` for interactive management and explicit-ID `packctl` commands for automation. Justfile recipes are development checks only; there is no public `MODPACK` context.
- Deployment SSH targets, stack paths, and Compose services must pass the shared validators in `packctl.py`; every SSH invocation uses `ssh -- <target> <command>`.
- Do not run `packctl deploy`, `packctl publish`, or `packctl restart` as verification: deployment uses remote `rsync -av --delete`, and restart invokes Docker Compose over SSH using values from the merged pack configuration.
