# Huroshiki v0.2.0-rc.1

## Highlights

This release candidate adds one-shot Template Import for existing Packs, loader-version-only
migration, canonical Modrinth search, and a substantially stricter process and transaction lifecycle.
It is intended for migration testing before the final v0.2.0 release.

## New Features

- Import ordered Templates into an existing Pack from `packctl apply-template` or **Pack -> Apply
  Template**. Huroshiki plans complete dependency closures, resolves source and side conflicts,
  previews the staged result, and publishes atomically without creating a persistent association.
- Preview or apply Packwiz loader-version migration while keeping the Minecraft version and loader
  type fixed. The same workflow is available under **Settings -> Versions**.
- Search Modrinth directly from Install and resolve IDs, slugs, and project URLs through an isolated
  provider process before invoking Packwiz.
- Configure deployment targets and Public Pack URLs from dedicated Settings screens or explicit
  `packctl` commands.
- Apply a requested side to the complete dependency closure for CLI, TUI, profile, Template
  composition, and Template Import additions.

Template Import was developed across [#67](https://github.com/upiscium/Huroshiki/pull/67) through
[#74](https://github.com/upiscium/Huroshiki/pull/74). Loader migration is covered by
[#65](https://github.com/upiscium/Huroshiki/pull/65) and
[#66](https://github.com/upiscium/Huroshiki/pull/66), and the settings work by
[#63](https://github.com/upiscium/Huroshiki/pull/63) and
[#64](https://github.com/upiscium/Huroshiki/pull/64).

## Reliability Improvements

- Provider and Packwiz processes run in isolated process groups with cancellation, absolute
  deadlines, SIGTERM/SIGKILL escalation, descendant detection, group-drain verification, and parent
  reaping. A zero child exit status is not accepted when cleanup integrity is incomplete.
- Noninteractive Packwiz commands are bounded to 120 seconds per process or one shared 600-second
  deadline for supported multi-command operations.
- PackTransaction discard is explicit, non-daemon, bounded, observable, idempotent, and retryable.
  Cleanup failure retains transaction state and the project lock rather than reporting false success.
- Update preparation, source copies, and snapshots run outside the Textual event loop and share
  cancellation/deadline checkpoints before navigation.
- Install checkpoint copying and resolver preparation run in the add-operation worker. Copy,
  resolution, URL download, interactive PTY polling, merge, rollback, and cleanup share one
  operation-wide absolute deadline. Generated trees move atomically into retained transaction state
  rather than being recursively deleted before navigation validates cleanup integrity; incomplete
  PTY termination keeps cleanup ownership until bounded navigation or discard cleanup succeeds.
- Source/configuration snapshots are revalidated, Pack source publication is atomic, settings use
  Linux compare-and-swap, and builds publish both distributions all-or-nothing.
- `nix flake check` includes the complete Python unit suite.

The bounded process and discard lifecycle changes are in
[#53](https://github.com/upiscium/Huroshiki/pull/53),
[#54](https://github.com/upiscium/Huroshiki/pull/54),
[#78](https://github.com/upiscium/Huroshiki/pull/78), and
[#79](https://github.com/upiscium/Huroshiki/pull/79).

## Breaking Changes

- Public interfaces are now clearly separated: `huroshiki` is the interactive TUI, `packctl` is the
  noninteractive CLI, and Just is development-only. `packctl use`, `packctl current`, `MODPACK`,
  public Just management recipes, and packaged `_just` completion are removed.
- Legacy Template Packwiz sources and `packctl migrate-template` are removed. Templates require a
  complete committed manifest and must not contain `templates/<id>/source`.
- Ignored local YAML accepts only documented machine-local operational keys. Unknown, identity, and
  semantic keys fail validation.
- Every project-specific noninteractive command requires an explicit Pack or Template ID. Provider
  roots use canonical IDs; CurseForge requires a numeric project ID.
- CLI update applies nothing when any resolver fails unless `--allow-partial` is explicit. Partial
  application returns status 2 and skips build.

## Migration

1. Back up the managed repository and ignored local configuration.
2. Convert legacy Template sources to complete committed `template.yaml` manifests, then remove each
   `templates/<id>/source` entry.
3. Remove prohibited local YAML keys and move semantic settings to committed manifests.
4. Replace Just management recipes and selected-project context with explicit `packctl` commands.
5. Validate the repository, every Pack, and every Template before building.

```bash
packctl validate
packctl list
packctl list-templates
packctl validate-for demo
packctl validate-template base
packctl build demo
```

See `CHANGELOG.md` and the README Just migration table for the complete procedure. Fix manifest or
local-configuration errors through their declared files; do not edit a real Pack source while an
operation is active.

## Known Issues

This RC does not include Template version migration (#80), complete Pack Minecraft/loader migration
(#81), or the comprehensive Content/KubeJS manager (#82). Existing basic UTF-8 content-file editing
is not the #82 content-management feature.

## Verification

The release preparation is gated by the focused release metadata test, the complete Python suite,
`nix flake check`, launcher syntax and actionlint checks, both Nix package builds, and installed
`--version`/`--help` smoke tests. The Nix smoke derivation also verifies all runtime helpers,
profiles, CSS, and both zsh completions while confirming `_just` is absent.
