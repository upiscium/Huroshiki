# Huroshiki v0.2.0-rc.2

## Highlights

- Added transactional Pack Content management, including browser/editor operations and local file or
  directory import.
- Added CurseForge project search with canonical numeric IDs and strict project-URL resolution.
- Added experimental Pack Minecraft/loader copy migration Core: target dependency resolution,
  conflict resolution, and digest-bound atomic target publication.

## Content Management

- Content changes are planned from snapshots and published atomically across common, client, and
  server overlays. Stale entries, unsafe files, portable collisions, and cross-side conflicts fail
  closed.
- The Content browser and bounded UTF-8 editor support safe create, delete, move, KubeJS presets,
  path details, and clipboard actions. Binary editing remains unsupported.
- Local file and directory import uses immutable, non-following source inspection, overwrite policies,
  conflict summaries, and transactional preview/apply.

## Provider Search

- Install search now supports CurseForge as well as Modrinth and carries canonical project IDs into
  resolution. Search results include title, author, and description; labels and slugs are not used as
  identity.
- CurseForge search and URL resolution require `HUROSHIKI_CURSEFORGE_API_KEY`, sent only as the API
  header, with Minecraft/loader filters and bounded provider-process cancellation.

## Experimental Pack Migration Core

The experimental copy-migration flow is:

```text
snapshot
  -> plan copy migration
  -> resolve target roots and dependency closure
  -> resolve unresolved roots with Remove / Replace
  -> prepare digest-bound publication
  -> atomically publish target Pack
```

- After the fixed source snapshot and any explicit root-provenance initialization are complete,
  planning, resolution, and publication do not modify the source Pack. Source and target locks are
  held in canonical order; target publication is no-clobber and does not copy operational deployment
  or server settings.
- Root provenance and complete target dependency closures are resolved against the target
  Minecraft/loader tuple. Unresolved roots require explicit Remove or canonical Replace choices;
  unresolved work does not modify formal staging.
- Stale snapshots, source mutations, target mutations, and changed migration attempts are rejected.
  Publication verifies the resulting target after atomic publication. Post-publication cleanup
  failures retain diagnostic state and support bounded cleanup retry.

## Reliability Improvements

- Content scans, staged writes, migration work, and cleanup use cancellation checkpoints and bounded
  deadlines outside the Textual event loop.
- Migration and Content transactions retain locks and diagnostic state when cancellation, cleanup,
  process termination, or publication integrity is uncertain instead of reporting false success.
- Install checkpoint preparation now keeps incomplete checkpoints, resolver trees, and staged sources
  in retained transaction state until bounded cleanup verifies their ownership and integrity.

## Compatibility and Behavioral Changes

- The existing loader-version-only migration remains the supported public migration workflow; it
  keeps Minecraft version and loader type fixed.
- A public migration CLI, TUI migration wizard, in-place migration, Template version migration, and
  migration-integrated remote Pack/server publication are not implemented in this release candidate.
- Experimental Pack migration Core does not copy deployment configuration or Minecraft server
  settings into the target Pack.

## Known Limitations

- Pack copy migration is experimental Core functionality, not a user-facing migration workflow.
- Binary Content editing is unsupported, and provider search requires the corresponding provider
  configuration and network access.
- The experimental Pack migration Core does not provide remote Pack or server publication.
