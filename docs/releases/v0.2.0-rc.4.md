# Huroshiki v0.2.0-rc.4

Release date: 2026-08-02

## Highlights

- Fixed the legacy Pack cross-provider dependency equivalence regression introduced in
  `v0.2.0-rc.3`.
- Preserved verified artifact and semantic JAR safety while allowing safe transitive dependency
  collisions in Packs created before root provenance manifests were introduced.
- Bound candidate provenance and existing-state into equivalence evidence.

## Legacy Pack compatibility hotfix

`v0.2.0-rc.3` rejected an Add when an existing Pack had no `.huroshiki-roots.json` and an incoming
transitive dependency collided with an equivalent dependency from the other provider. The reported
failure was:

```text
Cross-provider dependency equivalence requires explicit root provenance
```

`v0.2.0-rc.4` permits this safe verified transitive dependency collision. The fix is shared by Add,
Profiles, Template Import, and Update.

## Provenance and equivalence safety

Candidates now carry one of three provenance roles:

```text
explicit
dependency
unknown
```

For `existing unknown + incoming dependency`, Huroshiki preserves the existing metadata and
identity, unions sides, and omits the duplicate incoming metadata/JAR. It does not infer or create a
root manifest. An `unknown + incoming explicit root` collision remains ambiguous and is not
automatically merged; it fails closed before artifact materialization.

Equivalence verification remains mandatory. A collision may collapse only through one of:

- matching strict declared SHA-256 values;
- matching verified materialized SHA-256 values; or
- an exact complete target-loader MOD ID/version set.

Names, slugs, display labels, and filenames alone are never equivalence evidence. The evidence
binding includes each canonical candidate's provenance and existing-state together with metadata
digests, target context, and artifact or semantic JAR evidence. Canonical ordering keeps the binding
stable when candidate argument order changes.

## Unchanged behavior

- Packwiz-native CurseForge Install remains in the TUI, and no API key is required.
- Noninteractive CurseForge operations continue to require a positive numeric project ID.
- Explicit roots are not automatically collapsed with one another.
- URL-provider candidates remain outside automatic cross-provider equivalence.
- Cancellation, deadlines, process cleanup, transaction staging, and fail-closed verification retain
  their existing bounds.

## Known limitations

No live network-backed CurseForge install or cross-provider artifact collapse was executed as part
of release verification. Mocked and local artifact tests cover these paths.

## Upgrade notes

Legacy Packs do not need a manually fabricated `.huroshiki-roots.json` to receive this hotfix. Keep
existing metadata in place: verified incoming transitive dependencies can now merge safely without
promoting installed dependencies to roots. Ambiguous root replacement still requires explicit
provenance resolution.

## Verification

Release verification includes the complete Python test suite, Nix flake checks, both package builds,
launcher syntax and actionlint checks, repository validation, runtime version checks, release scope
auditing, and focused release metadata tests.
