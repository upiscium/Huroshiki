# Huroshiki v0.3.0-rc.1

Release date: 2026-09-03

This release candidate adds safer Copy migrations, exact MOD version intent, unified publication,
and more explicit transaction and cleanup lifecycles.

## Highlights

- Pack Copy migration creates a new Minecraft/loader target without modifying the source Pack.
- Template Copy migration creates a new target Template through a reviewed, one-shot flow.
- Pin exact Modrinth or CurseForge artifact versions and preserve that intent across supported
  operations.
- Preview and apply publication through one digest-bound CLI/TUI workflow.
- Retain diagnostic state when cleanup or remote publication outcomes cannot be proven.

## MOD version intent

Packs and Templates can record exact provider project and artifact IDs. Locked intent is a hard
constraint: an unavailable, incompatible, conflicting, stale, or orphaned exact choice fails closed
instead of being silently replaced. Unlocked intent may advance when the operation permits it.
Dependency intent remains dependency intent; it is not promoted to a root, and it is retained only
when required by a selected root. Newly carried intent is unlocked by default. Exact intent is
checked across Add, Update, Profiles, Template Import, and Copy migration.

## Pack and Template migration

`packctl migrate ... --copy-to ...` is Copy-only. It snapshots the complete source, locks source and
target in canonical order, resolves complete target dependency closures, and installs the target
without clobbering an existing project. Deployment and Minecraft-server settings are not copied;
the source remains unchanged. Legacy Packs without root provenance require explicit root selection,
and unresolved roots require explicit canonical Remove or Replace choices.

Template migration is also Copy-only: it creates a new target Template and does not migrate in
place. It is preview-first and one-shot, with explicit root choices, closure resolution, warning
acknowledgements, and atomic no-clobber publication. It does not create a persistent Template
association or content overlay.

Both CLI Copy commands default to preview; `--apply` publishes the reviewed copy. Copy migration
does not automatically build, deploy, publish, or restart anything.

## Publication

`packctl publish <pack>` is the sole publication operation. It builds the requested distribution,
creates one immutable plan, verifies the exact staged files, and activates the digest-bound remote
generation. Use `--preview` to plan without remote effects or `--yes` for noninteractive use.
Activation and server restart are reported separately; restart failure is not automatically retried.

The former standalone public `build`, `build-all`, `deploy`, `deploy-dry-run`, `deploy-all`, and
`restart` commands are retired. `packctl serve <pack> --port <port>` remains the supported local
path; it builds first and serves the distribution on loopback.

## CLI and TUI

The Installed MOD version browser provides exact-version browsing and intent controls, while Update
previews show current and candidate file IDs. The TUI also exposes Copy migration, publication
previews, cancellation-aware workers, and retained-state management. TUI and CLI publication use the
same previewed Core plan. `q` is the consistent idle back or active-cancel key across TUI screens.

## Reliability and transaction safety

Operations use snapshots, project locks, bounded deadlines, cancellation, isolated process groups,
and atomic publication where supported. Resolver failures, concurrent changes, incomplete process
termination, and invalid or stale evidence fail closed.

Publication uncertainty or cleanup failure is deliberately retained as diagnostic state with lock
ownership for bounded retry. This is not a guarantee of automatic rollback: an activated generation
may remain published while cleanup is unresolved, and an uncertain remote result is never retried or
reported as success.

## Compatibility / breaking changes

- The standalone public build, deploy, and restart commands are replaced by `packctl publish`.
- Exact MOD version intent is enforced as a constraint. Previously implicit artifact selection can
  now require an explicit compatible choice or fail closed instead of silently changing versions.

## Known limitations

- Template migration is not available in place; use Copy migration to create a new target.
- URL entries do not carry provider artifact version intent and remain bounded URL selections.
- CurseForge automation outside the TUI requires a positive numeric project ID; labels, names, slugs,
  and URLs are not accepted as identity.
- Publication requires configured remote distribution and restart targets. Publication and cleanup
  can remain in retained publication-uncertain or cleanup-pending state and require bounded retry or
  explicit retained-state cleanup; Huroshiki does not claim rollback when the remote outcome cannot
  be proven.

## Upgrade notes

- Replace old public build/deploy/restart command usage with `packctl publish`; use `packctl serve`
  for local serving.
- Pack and Template Copy migrations are available from the CLI and TUI and default to preview.
- Review exact MOD version intent and migration warnings before applying changes. Explicit intent can
  make a previously implicit artifact choice fail closed when no compatible exact version exists.
- No configuration-schema migration is required solely for this release candidate.

