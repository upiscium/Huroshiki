# Huroshiki v0.3.0-rc.2

Release date: 2026-09-08

This maintenance release candidate tightens publication integrity, includes Pack Content in final
Packwiz indexes, publishes independent client and server variants, and improves planning diagnostics.
It prepares source metadata only: the RC2 tag and GitHub Release do not yet exist.

## Highlights

- **#190 — Integrity:** immutable generations are checked against their bound manifests before
  reuse, and active generations are reverified after activation and before restart.
- **#192 — Pack Content:** common and side-specific Content is represented in the final generated
  `index.toml` with ordinary-file semantics and exact hashes.
- **#194 — Dual-variant publish:** one fixed source snapshot produces independent server and client
  identities. The server remains the publication root; the client is published at
  `publication_root/client`. Both variants are transferred and verified before activation, with
  activation ordered client first and server second. Restart occurs only after both variants verify.
  Cleanup is independent for each variant, and partial publication facts are retained for
  recovery and diagnosis.
- **#195 — Planning diagnostics:** resultless failures expose their direct `primary_error` while
  retaining orchestration context and the existing bounded, redacted diagnostic policy.

## Publication integrity

Before Huroshiki reuses a pre-existing generation, its files must still exactly match the manifest
bound to that generation. Publication-target provenance participates in target identity. After
activation, the active generation is checked again before restart. Remote verification also rejects
concurrent metadata or tree drift. A failure remains fail-closed, and uncertain restart outcomes are
still retained rather than reported as rollback or success. These checks do not identify a specific
external actor as the source of any earlier mutation.

## Dual-variant publication

`packctl publish <pack>` remains one operation. Its plan is built from one fixed source snapshot and
carries independent manifest and generation identities for server and client. The existing server
path remains the configured publication root; the client is published at
`<publication_root>/client`. Huroshiki transfers and verifies both variants before activation starts,
then activates and verifies client before activating and verifying server. Restart occurs only after
both active variants verify, so a client failure prevents restart. Cleanup authority and retained
facts are independent for each variant, and partial activation is not misreported as rollback.

## Content descriptors and indexes

Files from `content/common/**` and the selected side-specific Content tree appear in the final
generated `index.toml` as ordinary files with `metafile = false` and their exact SHA-256. The final
`pack.toml[index].hash` binds that final index, and semantic verification checks Content-backed
ordinary files. Descriptor generation has one deterministic final authority rather than competing
intermediate writers.

## Diagnostics

Publish preview and normal Publish now use the same diagnostic policy. Resultless planning failures
retain the high-level orchestration context and surface their direct `primary_error`; nested details
remain bounded and redacted, and absolute paths under the managed root are relativized. Existing
cancellation/deadline behavior and result-bearing publication, restart, and cleanup diagnostics are
unchanged.

## Compatibility and known limitations

- Existing server publication paths remain unchanged. `packctl publish <pack>` now also publishes
  the client variant beneath `<publication_root>/client`.
- There is no new `--target-side` primary workflow; use the dual-variant Publish operation.
- `distribution.public_pack_url` remains optional operator metadata and is not required for Publish.
- No configuration-schema migration is required solely for these maintenance changes.
- Publication uncertainty does not claim or perform a false rollback. Retained facts may require
  bounded recovery or cleanup.
- Separate publication and restart hosts do not provide a cross-host atomic lock.
- Reverse-proxy and public URL mapping remain explicit operator configuration rather than being
  inferred from the rsync target.
