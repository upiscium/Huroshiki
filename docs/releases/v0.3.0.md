# Huroshiki v0.3.0

Release date: 2026-09-11

Huroshiki v0.3.0 is the first stable release of the tested 0.3.0 release-candidate line. It
consolidates the Pack/Template management, migration, publication, transaction-safety, and provider
workflows exercised through v0.3.0-rc.1 and v0.3.0-rc.2.

This commit prepares stable source metadata only. The `v0.3.0` annotated tag and GitHub Release do
not yet exist. There are no functional runtime or Publish changes between `v0.3.0-rc.2` and this
stable preparation; the promotion changes release metadata and documentation only.

## Highlights

- `huroshiki` remains the interactive TUI and `packctl` the noninteractive automation boundary;
  project-specific commands use explicit Pack or Template IDs.
- Pack Content supports safe common/client/server overlays with bounded UTF-8 editing and import,
  collision detection, no-follow filesystem policy, and transactional publication.
- Provider resolution uses canonical Modrinth or CurseForge identities, complete dependency
  closures, exact version intent, and verified cross-provider dependency equivalence.
- Template Import and Pack/Template Copy migration are preview-first, explicit, transactionally
  applied workflows with fixed source snapshots and canonical root provenance.
- `packctl publish <pack>` is the sole publication operation. One fixed source snapshot produces
  independent server and client variants, verifies both, activates client then server, and restarts
  only after both active variants verify.
- Publication and transaction failures retain bounded recovery evidence rather than claiming false
  rollback or success.

## Pack and Template workflows

Huroshiki manages Packwiz Packs and manifest-based Templates in one repository. Add, Update,
Profiles, Template Import, version migration, and Copy migration preserve canonical provider/project
identity and fail closed on stale, incompatible, ambiguous, or conflicting state.

Exact MOD artifact intent can be represented by Modrinth version ID or CurseForge file ID. Locked
choices remain hard constraints while unlocked choices may advance where the operation permits.
Template Import reconstructs one final constraint set after conflict resolution and applies the
result atomically without creating a persistent Template association.

Pack Copy migration changes Minecraft/loader targets by constructing a new target Pack rather than
mutating the source. Template Copy migration similarly creates a new resolved Template target.
Source snapshots remain immutable during planning, existing targets are never clobbered, and
operational deployment/server settings are not copied into new Packs.

## Publication architecture

`packctl publish <pack>` builds one immutable, network-free plan from one fixed source snapshot.
Server and client use independent manifest and generation identities. The configured publication
root remains the server namespace while the client variant is published beneath
`<publication_root>/client`.

Both variants transfer and verify before activation starts. Activation is ordered client first and
server second, followed by active-generation verification. Restart is attempted only after both
active variants verify. Cleanup authority and retained facts remain independent for each variant,
and partial publication or restart uncertainty is never reported as rollback.

An existing immutable generation is reusable only while its filesystem state still matches the
manifest bound to that generation. Target provenance participates in identity, active generations
are reverified before restart, and concurrent remote metadata or tree drift fails closed.

## Pack Content descriptors

Files from `content/common/**` and the selected side-specific Content tree are included in the final
Packwiz `index.toml` as ordinary entries with `metafile = false` and exact SHA-256 values. The
`pack.toml[index].hash` binds the final generated index, and semantic verification covers the
Content-backed files.

## Diagnostics and failure handling

Publish preview and normal Publish share the same bounded, redacted diagnostic policy. Resultless
planning failures keep high-level orchestration context while exposing their direct `primary_error`;
managed-root absolute paths are relativized. Cancellation, deadlines, result-bearing publication,
restart, and cleanup diagnostics retain their existing semantics.

Resolver, Packwiz, rsync, SSH, transaction, and cleanup work is bounded by cancellation/deadline
rules and explicit ownership. Cleanup-pending and publication-uncertain state preserves diagnostic
and lock ownership when completion cannot be proven.

## Compatibility and known limitations

- Existing server publication paths remain unchanged; the client variant is under
  `<publication_root>/client`.
- There is no primary `--target-side` Publish workflow. One Publish operation handles both variants.
- `distribution.public_pack_url` is optional operator metadata and is not required for Publish.
- Reverse-proxy/public URL mapping remains explicit operator configuration and is not inferred from
  the rsync target.
- Separate publication and restart hosts do not provide a cross-host atomic lock.
- Publication uncertainty does not perform or claim a false rollback; retained state may require
  bounded recovery or cleanup.
- No configuration-schema migration is required solely for the RC2-to-stable promotion.

## Production evidence

The RC2 production smoke established independent server/client publication and subsequent clean
active generations with no smoke residue. The current clean active generations were also checked
against their descriptors: both server and client `pack.toml[index].hash` values matched the
physical `index.toml` SHA-256 values.

The retained smoke generations required for the final Content-descriptor gate are still present.
Before stable publication, directly confirm that common and side-specific smoke entries have the
expected side placement, `metafile = false`, and physical-file SHA-256 values, with wrong-side
entries absent. This preparation does not claim that final per-entry production check has passed.
