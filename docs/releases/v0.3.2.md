# MATOI v0.3.2

Release date: 2026-10-11

This commit prepares stable source metadata only. The `v0.3.2` tag and GitHub Release do not yet exist.
Release publication is a separate step after the exact release candidate has passed its checks.
Existing v0.3.1 history is not retagged or rewritten.

## Highlights

- MATOI (纏) branding and the preferred `matoi` command, with existing `huroshiki`, `packctl`,
  `HUROSHIKI_*` and Nix compatibility aliases retained.
- Correct exact Add resolution ordering and same-artifact root promotion (#208, #212).
- Full post-refresh integrity checks, authoritative root/side handling, stable version locks/reasons,
  valid Packwiz indexes, and reusable rollback after failed operations (#214, #215, #216).
- One-shot migration navigation and real destination-readiness checks; accurate PTY child exit,
  startup diagnostics and cleanup verification (#217, #218).

## Upgrade and compatibility

Do not rename `.huroshiki/`, `.huroshiki-roots.json`, `.huroshiki-version-overrides.json`, or
`[huroshiki]` metadata. Internal namespace migration remains deferred in #211. Back up managed
Pack data as usual and verify it with `packctl validate-for <pack-id>` after upgrading.

Re-adding an identical installed artifact with already-covered sides records provenance/version
intent without changing installed MOD descriptors or re-resolving unrelated roots. It is not a
certification or repair of pre-existing runtime dependency health. Additional sides or different
artifacts use full exact verification. A subset re-add never narrows existing distribution.

Legacy Packs without root provenance remain readable; role display is unavailable until provenance
is explicitly recovered. The release does not fabricate root history or silently select every MOD.

## Verification boundaries

The release audit is tracked in #213. Code qualification uses pinned revisions, full Nix/unit checks,
configured independent reviewer roles, and isolated copies of real Packs on Adam. Historical failed
runs and deterministic repro evidence remain recorded; release preparation is not itself a passing
verification receipt for an unpublished tag.

The PTY test now permits up to 30 seconds for cold Python/Textual startup, then retains a separate
five-second control-input/actual-exit budget. Raw flags, control-key order, termios restoration, and
zero actual exit remain required. No runtime timeouts or the separate URL deadline assertion were
relaxed. The old empty-output failure was not conclusively attributed to host load.

No live Publish, rsync activation, Docker restart, or production Pack mutation is performed by this
metadata preparation. Linux x86_64 is the audited runtime; do not infer an aarch64 execution result.
